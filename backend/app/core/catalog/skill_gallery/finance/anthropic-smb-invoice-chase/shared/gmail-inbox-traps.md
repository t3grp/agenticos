# Mail evidence and inbox checks

The pinned source described a particular Gmail connector's label-search behavior. Treat it as a validation example, not a universal Gmail API rule.

## Empty label results

Inspect the active search schema to determine whether it accepts a label ID, name or query expression. Confirm the label exists and compare a bounded query with its reported count. A source example found `label:Label_2` empty while `label:Leads` returned 201 threads; another connection may use a different contract. Do not claim no invoices exist from one unexplained empty result.

## Count the right population

Distinguish human correspondence, invoices, payment notices, bulk mail and authentication messages. Do not treat a raw thread count as an inquiry or invoice count. Do not discard an invoice merely because it was automatically sent: machine-generated billing messages can be core AP evidence. Read accessible attachments and record any coverage gap.

## Authentication material

Do not copy one-time passwords, password-reset links, magic sign-in links, API keys or tokens into accounting outputs. Count or describe them by category only when relevant. Do not mark a message handled, archived or read unless an authorized action actually occurred; this pack reads and prepares only.

## Payment-detail changes

Surface a changed bank account, payee or urgent payment request as a verification exception, without reproducing full sensitive account details. Use a trusted channel already on file for the review recommendation; do not accept the new contact details as their own verification. See `untrusted-content.md` and `personal-data.md`.
