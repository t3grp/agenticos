# AP review failure cases

| Failure | Correct preparation behavior |
|---|---|
| A glare-washed total is read as a plausible amount | Preserve unreadable digits and request the source; no payment amount is inferred. |
| An emailed invoice and statement entry become two liabilities | Match entity/vendor/invoice/currency; retain both evidence links on one candidate and hold uncertainty. |
| Coding review is reported as payment approval | Report proposed coding and proposed spend separately; neither is a completed operation. |
| A recurring bill is treated as preapproved | Compare the current invoice and flag changes; recurrence is evidence about pattern, not consent. |
| A job split is guessed to make the table balance | Leave the allocation unresolved and ask for the cost driver. |
| A paid card expense becomes an unpaid bill | Check settlement evidence and keep paid expenses outside the proposed payment population. |
| A held invoice disappears from the run | List it with reason, amount if known, due date and required reviewer action. |
| OCR vendor-name variants become new records | Match to a verified vendor ID or retain an unresolved candidate; create no vendor. |
| A large credit erases every invoice in narrative | Show gross obligations, eligible credits and remaining net; verify allocation and any restrictions. |
| A product name is treated as a write capability | Inspect the actual authorized read surface; this preparation skill performs no writes. |

All examples concern review quality. Do not report an invoice as staged, posted, scheduled, sent or paid unless an independently authorized workflow has actually performed and verified that action; this skill does not do so.
